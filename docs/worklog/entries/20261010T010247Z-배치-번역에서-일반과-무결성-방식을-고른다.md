## 배경

배치 모드(2026-09-24)는 표준 모드 청크를 표준 모드 프롬프트로만 보냈다. 사용자는 배치로 보낼 때 일반과 무결성 중 하나를 자유롭게 고를 수 있어야 한다고 요구했다. 무결성 모드는 줄마다 ID를 붙인 JSON을 보내고 응답 스키마를 강제하며, 누락 줄 재요청·검열 이진 분할·과부하 대기로 복구한다.

## 문제

1. 무결성 요청 조립과 응답 해석이 실시간 호출 함수 안에 묶여 있어 배치가 같은 요청을 만들 수 없었다. 배치 모드 도입 때 표준 경로에서 했던 분리를 무결성 경로는 거치지 않았다.
2. 무결성 복구 장치 셋은 모두 응답을 보고 곧바로 다시 부르는 구조라 배치 안에서 돌 수 없다.
3. 무결성 결과는 출력 경로 옆 임시 폴더에, 배치 상태는 입력 파일 메타데이터에 있다. 제출과 수거 사이(최대 24시간)에 출력 경로나 청크 설정이 바뀌면 결과가 다른 폴더나 다른 자리로 간다.
4. 실시간 무결성 이어하기는 청크 파일이 있는지를 번호로만 봤다. 청크 크기나 최대 항목 수가 바뀌면 옛 파일이 다른 줄 범위를 담는데도 그 청크를 완료로 건너뛰어, 해당 줄이 조용히 원문으로 남았다. 배치는 설정이 바뀔 틈이 길어 이 구멍에 더 자주 닿는다.
5. 무결성 요청의 응답 스키마는 파이썬 타입(TranslatedUnit 리스트)이다. 실시간 호출은 SDK가 전송 순간 스키마 객체로 바꾸지만, 배치는 요청을 먼저 만들어 크기를 재는데 그 직렬화가 이 타입에서 실패했다.

## 결정과 근거

- 무결성 요청 조립과 응답 해석(코드펜스 제거, 괄호 추출, 정규식 복구, 래퍼 언래핑, 누락 계산)을 실시간·배치 공용 함수로 뺐다. 실시간 경로도 같은 함수를 써서 두 경로의 프롬프트가 갈라지지 않는다. 동작 변화 없는 리팩터이며 기존 무결성 테스트로 확인했다.
- 복구는 배치 한 번 + 실시간 무결성 마무리로 나눴다. 수거 결과는 완전·부분·실패로 가른다. 완전하면 실시간과 같은 청크 파일에 쓰고, 실패(검열·빈 응답·해석 불가)는 실패 기록만 남긴다. 부분 청크는 받은 줄을 별도 파일(partial_<i>.json)에 두고, 마무리 때 빠진 줄만 누락 재요청 단계(retry_depth 1)부터 묻는다. 배치 응답을 첫 시도로 치면 실시간의 첫 요청 + 누락 재요청 예산과 같아진다. 누락 재요청을 꺼 둔 설정이면 실시간처럼 빠진 줄을 원문으로 두고 완료한다.
- 부분 결과 파일 이름은 chunk_*.json 패턴을 피했다. 실시간 이어하기·검토 탭·기억 복원이 그 패턴을 완료로 읽기 때문이다.
- 이어하기의 완료 판정을 바꿨다. 청크 파일은 그 청크의 비공백 줄 ID를 모두 담을 때만 완료다. ID는 파일 전체의 줄 번호라 경계가 바뀌어도 포함 여부로 가릴 수 있다. 실시간 이어하기, 배치 요약, 번역 기억 복원이 같은 판정을 쓴다. 한쪽만 바꾸면 배치는 미완료로 보는 청크를 실시간 마무리가 건너뛴다.
- 번역 방식은 배치 항목에 기록하고, 진행 중인 배치의 조회·수거·재제출·마무리는 설정이 아니라 기록된 방식을 따른다. 설정과 다른 방식으로 시작 버튼을 누르면 새 배치로 시작한다. 이전 작업 목록은 다른 청크 경계를 가리키므로 버린다. GUI는 진행 중에 방식 선택을 잠근다.
- 무결성 배치는 제출 때 출력 경로를 기록하고, 수거·마무리·그대로 저장에서 다른 출력 경로를 받으면 거부한다. 그대로 두면 실시간 마무리가 빈 임시 폴더를 보고 전부 다시 번역한다.
- 제출 때 청크 경계와 원문의 지문을 기록하고, 수거할 때 달라졌으면 거부한다(두 방식 모두). 결과는 청크 번호로 돌아오므로 경계가 바뀌면 다른 원문 자리에 쓰인다. 이전 표준 배치는 이 경우를 조용히 잘못 기록했다.
- 실시간 마무리는 진행 중인 배치 작업이 있으면 막는다. 같은 청크가 두 번 과금된다.
- 무결성 그대로 저장은 실패 표시를 끼우지 않고 원문 줄을 둔다. 받은 일부 줄의 번역은 쓴다. 무결성 방식의 핵심인 줄 위치를 지키기 위해서다.
- 응답 스키마는 배치 요청을 만들 때 SDK의 변환 함수로 미리 스키마 객체로 바꾼다. 이 함수가 클라이언트 인자를 쓰는 곳은 개발자 API에서 쓸 수 없는 속성 검사뿐이라 결과가 실시간 경로와 같다. SDK 내부 모듈에 기대므로 배치 클라이언트 모듈 한 곳에 두었다.

버린 접근:

- 복구까지 배치 라운드로 처리하는 방안(빠진 줄만 모은 요청, 검열 청크의 반쪽 요청을 다음 라운드로). 결과가 줄 ID로 합쳐져 병합은 쉽지만, 분할 깊이와 누락 재요청 예산을 라운드를 넘어 저장해야 하고 라운드마다 최대 24시간이라 최악에는 며칠이 걸린다. 나중에 재제출을 "빠진 줄만 재제출"로 넓히는 정도로 남겼다.
- 응답 스키마를 JSON Schema 사전(response_json_schema)으로 보내는 방안. 직렬화 문제는 풀리지만 실시간 경로가 쓰는 형식과 달라지고, 배치에서 $ref 처리 등이 같은지 확인할 수 없어 버렸다.
- 새 모드 카드(배치 무결성)를 두는 방안. 배치는 파이프라인과 별개인 전송 방식이라, 배치 패널 안의 선택지로 두었다.

## 검증

- 기준선 483 passed, 7 skipped에서 변경 후 503 passed, 7 skipped.
- 가짜 배치 서버 통합 테스트 8개: 무결성 제출(줄 ID JSON, 스키마 객체, 출력 경로 기록) → 부분·검열 수거 → 실시간 무결성 마무리가 빠진 줄 4와 검열 청크만 묻고 줄 위치가 맞는 결과, 전부 성공 시 자동 저장과 무결성 검토 화면, 그대로 저장의 줄 위치, 누락 재요청을 끈 설정, 방식 전환과 재제출의 방식 유지, 출력 경로 거부와 진행 중 마무리 거부, 경계 변경 시 수거 거부, SDK 변환 후 responseSchema가 ARRAY로 나감.
- 이어하기 도메인 테스트 3개(옛 경계 파일 재번역, 부분 결과의 빠진 줄만 요청, 누락 재요청 예산). 수정 전 코드에서는 3개 모두 실패했다.
- 설정 탭 테스트 3개(방식 저장·불러오기, 진행 중 잠금과 방식 표시, 방식이 다를 때 안내와 누락 열).
- SDK 2.24.0에서 배치 요청 변환이 응답 스키마를 실시간과 같은 객체로 바꾸는 것을 직접 확인했다.
- 실제 Batch API로는 검증하지 않았다. 배치에서 응답 스키마(id의 anyOf 포함)가 실제로 적용되는지는 SDK 변환 단계까지만 확인했다.

## 미해결

- 실제 Batch API 호출 검증. 무결성 청크 몇 개를 제출해 스키마 적용과 응답 형식을 보는 것이 첫 단계다.
- 배치 1라운드 요청은 제출 시점에 한꺼번에 만들어져, 실시간 무결성처럼 앞 청크의 번역이 뒤 청크의 기억 예시가 되지 못한다. 호칭·말투 일관성이 실시간보다 낮을 수 있다.
- 무결성 배치 뒤 일반 방식으로 바꾸면 일반 쪽 진행이 새로 시작된다(실시간 표준 모드가 무결성 실행 뒤에 하는 것과 같다). 메타데이터 하나를 두 방식이 나눠 쓰는 구조 때문이다.
- 배치 모드가 아닌 실시간 시작 버튼은 진행 중인 배치 작업이 있어도 막지 않는다. 막는 것은 배치 패널의 실시간 마무리뿐이다.
- 모델이 청크 밖 줄 ID를 지어내는 경우, 배치 수거는 그 청크의 줄만 남기지만 실시간 무결성 경로는 지금도 그대로 합친다.
