## 배경

RPM 제어 리팩터 T7이다. T3 이후 API 요청은 GeminiClient의 스케줄러가 한 번에 하나씩 보낸다.

## 문제

동시성 제한이 층마다 따로 걸려 있었다.

- 번역 경로: 앱 번역 루프의 세마포어(max_workers) 안에서, 검열로 분할하면 `_translate_with_recursive_splitting_async`가
  세마포어(max_workers)를 새로 열고, 서브 청크가 다시 검열이면 재귀 호출마다 또 연다. 동시 작업이 층마다 곱으로 늘 수 있었다.
- 검수 경로: GUI 검수 탭의 세마포어 안에서 EPUB 프로바이더가 서브 청크마다 세마포어를 또 열었다.

요청은 어차피 한 번에 하나씩 나가므로, 안쪽 층에서 병렬로 띄워도 빨라지지 않고 대기 태스크만 늘어난다.

## 결정과 근거

- 동시 작업 수는 가장 바깥 진입점만 제한한다. 앱의 용어집·번역 루프, GUI 검수 탭의 일괄·선택 재번역 네 곳이다.
- 안쪽 두 곳(서브 청크 분할, EPUB 서브 청크 재번역)은 세마포어와 태스크 관리 코드를 없애고 순서대로 처리한다.
  순서가 곧 결과 순서라 정렬 코드도 필요 없어졌다. EPUB은 이전처럼 한 서브 청크가 실패해도 나머지를 계속하고,
  실패한 줄은 원문으로 둔다.
- 동작이 바뀐 두 곳:
  - 서브 청크 사이에서 중단 요청을 받으면 `BtgTranslationException("서브 청크 번역이 취소되었습니다.")`를 던진다.
    예전에는 태스크를 만드는 도중에 중단되면 만들어진 태스크의 결과만 이어 붙여 **일부만 번역된 결과를 정상처럼
    돌려줄** 수 있었다.
  - 태스크가 실제로 취소되면(`CancelledError`) 그대로 전파한다. 예전에는 `BtgTranslationException`으로 바뀌어,
    바깥에서는 취소가 아니라 실패로 보였다.
- GUI 검수 탭이 동시성을 직접 관리하는 것은 남겨 두었다. 오케스트레이션을 AppService로 옮기는 일은 이번 범위보다 크다.

## 검증

- 새 테스트 5개: 서브 청크의 최대 동시 진행이 1이고 결과가 원래 순서대로 이어짐, 검열 오류 뒤 재귀 분할도 동시 1,
  서브 청크 사이 중단 요청, 태스크 취소 전파, EPUB 서브 청크의 순차 처리와 실패 시 원문 유지.
- 예전 코드로 되돌려 같은 테스트를 돌리면 5개 중 4개가 실패한다(동시 진행 수 초과, 취소 전파 없음).
- 작업 중 재귀 분할 테스트가 한 번 실패했다. 가짜 번역 함수가 "처음 보는 텍스트면 실패"여서 재귀로 생긴 더 작은
  텍스트도 계속 실패했기 때문이다. 전체에서 한 번만 실패하도록 테스트를 고쳤다.
- 전체 pytest: 155 passed, 새 실패 없음.

## 미해결

- GUI 검수 탭의 두 세마포어는 GUI 계층에 남아 있다.
- 실제 키로 번역·검수 흐름을 돌려 보지는 않았다(T8).
