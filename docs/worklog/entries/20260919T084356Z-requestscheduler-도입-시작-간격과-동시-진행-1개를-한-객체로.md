## 배경

RPM 제어 리팩터(T1~T8)의 T2다. 사용자 대부분이 무료 티어 키 여러 개를 돌려 쓰므로, 여러 키로
동시에 요청이 나가면 구글이 악성 사용자로 판정할 수 있다. 전체 RPM은 의도적으로 낮게(예: 1.8) 둔다.

## 문제

기존 `GeminiClient._apply_rpm_delay`는 요청 **시작 시각의 간격**만 조절한다. thinking=high 요청은
간격(33초)보다 오래 걸릴 수 있어 여러 요청이 동시에 진행된다. 지금은 키가 고정이라 같은 키 안에서만
겹치지만, 후속 단계(T4)에서 새 요청마다 키를 바꾸면 곧바로 키 간 병렬 호출이 된다. T1 특성 테스트
`test_slow_requests_overlap_in_flight`가 이 겹침을 고정해 두었다.

## 결정과 근거

- 락을 먼저 잡고 그 안에서 간격을 기다린다. 다음 시작 시각은 max(앞 요청 종료, 앞 요청 시작 + 간격)이
  되어, 겹침이 구조적으로 불가능하다. 대기 순서는 `asyncio.Lock`의 도착 순서를 따른다.
- **버린 접근: 선예약.** 구 `_apply_rpm_delay`는 대기 전에 다음 슬롯 시각을 먼저 기록한다. 이 방식은
  대기 중 취소된 요청도 슬롯을 소비해, 뒤 요청이 한 간격을 더 기다린다. 대기가 끝난 뒤에 시작 시각을
  기록하도록 바꿨고, 취소된 요청은 슬롯을 쓰지 않는다. 락 안에서 기다리므로 선예약 없이도 순서가 보장된다.
- 동시 진행 상한은 설정값이 아니라 1로 고정했다. 설정으로 열면 오용 시 병렬 호출이 되므로, 필요해질 때
  확장한다.
- RPM이 없거나 0 이하여도 동시 진행 1개는 지킨다. RPM 제한 해제가 병렬 허용을 뜻하지 않게 하기 위함이다.
- 시계와 대기 함수를 생성자로 주입받는다. T1에서는 모듈의 `time`·`asyncio`를 프록시로 바꿔 끼웠는데,
  주입 방식이면 테스트가 전역 상태를 건드리지 않는다. T1의 가상 시계는 공용 헬퍼로 옮겨 두 테스트가 같이 쓴다.
- 로그 문구 "RPM(x) 제어: 다음 요청까지 N초 대기합니다. (예약된 시작: …)"와 1초 기준 INFO/DEBUG 구분을 유지했다.

## 검증

- 단위 테스트 14개: 시작 간격, RPM 1.8의 33.33초, 느린 요청의 비중첩, max(종료, 시작+간격),
  RPM 없음에서도 직렬화, 도착 순서, 대기열 취소와 간격 대기 중 취소, 예외 시 슬롯 반환, 로그 레벨·문구.
- 변형 확인: 락 제거(7개 실패), 간격 대기 제거(8개 실패), 구 선예약 방식 복원(취소 테스트 실패)을 모두 잡는다.
- 전체 pytest: 새 실패 없음. tkinter GUI 테스트 5개가 실행마다 FAILED와 ERROR 사이를 오가는 것은 기존 현상이다.

## 미해결

- 아직 `GeminiClient`에 연결하지 않았다(T3). 연결 전까지 실제 요청은 여전히 겹칠 수 있다.
- 요청이 걸리면 전체가 멈춘다. `api_timeout` 기본값(config 1000초)이 길어 최대 수십 분을 막을 수 있다.
