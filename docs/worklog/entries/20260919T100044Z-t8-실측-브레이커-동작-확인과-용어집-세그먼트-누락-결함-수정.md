## 배경

RPM 제어 리팩터 T8이다. T1~T7의 동작을 실제 API로 확인한다. 사용자 설정(키 45개, RPM 1.8, gemini-3.8-flash)을
복사하되 `max_workers`를 3으로 올리고 용어집 세그먼트를 700자로 잘라, 직접 쓴 일본어 판타지 단편(2,473자, 4세그먼트)으로
`main_cli.py --extract_glossary_only`를 실행했다. 키가 든 설정 복사본은 실행 뒤 지웠다.

## 문제

첫 실행(3분 40초, 요청 7회 중 503 4회)은 "성공"으로 끝났지만, 503 두 번으로 실패한 세그먼트 1에만 나오는 고유명사
(アシュフォード, シルヴァ, グレイン, ロウェル)가 결과 용어집에 하나도 없었다. 원인은 T5b의 전제다. 503 재시도 소진을 청크 단위
실패로 두고 "이어하기로 다시 처리된다"고 봤는데, 번역에는 이어하기가 있지만 용어집 추출에는 없다. 용어집 루프는 원래부터
어떤 예외든 세그먼트를 로그만 남기고 버렸고, T5b가 503을 곧바로 세그먼트 실패로 바꾸면서 이 결함이 자주 드러나게 됐다.

## 결정과 근거

- AppService 용어집 루프가 세그먼트마다 (번호, 결과, 오류)를 돌려받아 실패를 모은다. `asyncio.as_completed`가 원래 태스크가
  아닌 대기 객체를 돌려줘 태스크로 번호를 역추적할 수 없어서 이렇게 했다(처음 쓴 역추적 코드는 실행 전에 버렸다).
- 첫 순회 뒤 **과부하(503)로 실패한 세그먼트만** 한 번 더 시도한다. 과부하가 이어지면 서킷브레이커가 요청을 막아 두므로
  재시도가 쿼터를 낭비하지 않는다. 검열·요청 오류 등은 다시 보내도 결과가 같을 가능성이 높아 재시도하지 않는다.
  과부하 여부는 예외 사슬(`original_exception`, `__cause__`)에서 `GeminiServiceUnavailableException`을 찾아 판단한다.
- 그래도 빠진 세그먼트가 있으면 "세그먼트 N/M개가 실패해 결과에서 빠졌습니다 (번호 […])"를 경고로 남기고, 마지막 진행
  상태 메시지를 "완료 (세그먼트 N개 누락)"로 보낸다. 취소 시 중간 결과를 저장하는 기존 동작은 유지했다.

## 검증

- 첫 실행: 요청 간격 6개가 모두 33.3~33.4초, 새 요청 키 #1→#2→#3→#4, 재시도는 같은 키, 503 재시도 1회 후 그 세그먼트만 실패하고
  작업 계속, 백오프 중 다른 요청이 먼저 나감. 모든 응답이 21초 안에 와서 비중첩은 실측으로 확인하지 못했다(단위 테스트로만).
- 두 번째 실행(수정 후): 과부하가 심해 **서킷브레이커가 실제로 동작**했다. 연속 503 3회에서 5분 정지 → 정지 뒤 첫 요청도 503이라
  10분 → 다시 503이라 20분. 17분 동안 요청은 6회뿐이었다. 20분 정지 중에 검증용으로 건 25분 실행 제한에 걸려 강제 종료되어,
  **수정한 재시도 경로와 누락 경고는 실측으로 확인하지 못했다.** 그때까지 세그먼트 1 성공, 2·3 실패, 4는 재시도 대기 중이었다.
- 단위 테스트 6개: 과부하 세그먼트를 끝에 재시도해 전부 수집, 재시도도 실패하면 경고와 "N개 누락" 상태, 검열 실패는 재시도하지
  않되 누락 경고, 전부 성공, 예외 사슬 판별, 취소 시 중간 저장. 수정 전 코드에서는 앞의 5개가 실패한다.
- 전체 pytest: 161 passed, 새 실패 없음.

## 미해결

- 과부하가 길면 정지가 5→10→20→30분으로 늘어나 짧은 작업도 한 시간 가까이 걸릴 수 있다. 쿼터는 지키지만 대화형 사용에는 길다.
  최대 정지 시간이나 "정지 N회 뒤 작업 포기" 같은 상한은 사용자 결정이 필요하다.
- 클라이언트가 성공 응답을 로그에 남기지 않아 응답 시간을 다음 로그 줄로 추정했다. 요청 로그의 "(시도: n/6)" 분모는 503(최대 2회)과
  맞지 않는다.
- 3회·5분·30분 값의 적정성은 이번 두 실행만으로 판단하기 이르다.
