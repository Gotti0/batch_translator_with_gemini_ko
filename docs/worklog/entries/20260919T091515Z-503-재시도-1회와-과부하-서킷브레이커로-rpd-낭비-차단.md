## 배경

RPM 제어 리팩터 T5b다. 로컬 로그를 (키, 태평양 날짜, 모델)별로 집계한 결과 503도 무료 티어 하루 한도를 1회씩
쓰는 것으로 보였다. 503이 많던 날 키들은 성공 6~13회 만에 하루 한도에 걸렸고 성공과 503을 합하면 20 근처였다.
사용자들이 가장 아까워하는 낭비다. 요청 전에 서버 부하를 알 공식 수단은 없다(AI Studio 상태 페이지는 장애 이력만,
`models.get`·`count_tokens`는 생성 용량과 무관, probe는 그 자체가 쿼터를 씀).

사용자 확정: 503 재시도는 요청당 1회, 서킷브레이커는 연속 3회·5분·최대 30분이며 값은 설정으로 둔다.

## 문제

1. 503 재시도를 다 쓴 요청을 어떻게 끝낼지. T4에서는 서킷브레이커가 없어 작업 전체를 멈추는 쪽을 택했다. 그대로
   두면 한 청크가 503을 두 번 받는 것만으로 번역 작업 전체가 멈춘다.
2. 브레이커에 결과를 언제 기록할지. 슬롯을 놓은 뒤(except)에 기록하면 이론상 다음 요청이 먼저 슬롯을 받을 수 있다.

## 결정과 근거

- 503 재시도 소진은 새 예외 `GeminiServiceUnavailableException`(`GeminiApiException` 직속)으로 끝낸다. 키 소진 계열이
  아니므로 호출부는 그 청크만 실패로 남기고 작업을 계속한다. 이어하기가 `translated_chunks`에 없는 청크를 모두 다시
  처리함을 코드로 확인했다(실행 확인은 안 함). 과부하가 이어지면 다음 요청은 브레이커가 멈춘다.
- timeout 같은 다른 일시 오류는 T4 동작(요청당 max_retries회 후 작업 중단 예외)을 유지한다. 이들이 쿼터를 쓰는지는
  확인하지 못했다.
- 브레이커는 스케줄러와 별개 객체다. 스케줄러는 슬롯을 내주기 전에 브레이커가 준비될 때까지 기다리고(락을 쥔 채,
  취소에 반응), 브레이커는 연속 503만 센다. 503이 아닌 응답(성공, 429, 500, timeout)은 연속을 끊는다.
- 기록은 슬롯 안에서 API 호출을 감싸 한다(`with breaker.observe():`). 우리 쪽에서 요청 전에 던지는 예외(키 없음 등)는
  서버 응답이 아니므로 세지 않고, 취소도 세지 않는다. `list_models`는 메타데이터 조회라 감싸지 않았다.
- 정지가 끝나면 half-open: 동시 진행 1개라 자연히 요청 한 건이 상태를 확인한다. 503이 아니면 닫고 정지 시간을 처음
  값으로 되돌리고, 503이면 정지 시간을 두 배로 늘려(최대 30분) 다시 연다.
- 값은 `overload_pause_threshold`(3), `overload_pause_seconds`(300), `overload_max_pause_seconds`(1800)로 설정에 두고
  AppService가 클라이언트에 넘긴다. GUI 설정 화면에는 넣지 않았다.

## 검증

- 브레이커 단위 테스트 12개(임계값, 503 아닌 결과의 초기화, half-open 성공·실패, 두 배 증가와 상한, 취소 무시, 로그,
  스케줄러 대기와 대기 중 취소).
- 특성 테스트: "503이 계속되면 같은 키로 재시도 후 작업 중단" 테스트를 둘로 나눴다. 503은 2회 시도 후 이 요청만 실패,
  timeout은 기존대로 재시도 소진 후 작업 중단 예외. 브레이커 시나리오 4개 추가: 요청 A가 503 두 번, 요청 B의 첫 503이
  연속 세 번째가 되어 B의 재시도가 정확히 300초 뒤에 나감 / 503 아닌 응답이 연속을 끊음 / 정지 뒤 첫 요청도 503이면
  600초 / 할당량·500 오류는 브레이커를 열지 않음.
- 변형 확인 5종(열리지 않음, 두 배 증가 제거, 스케줄러가 브레이커 무시, 503 재시도 제한 제거, 503 아닌 오류가 연속을
  끊지 않음) 모두 잡힌다. 처음 돌린 변형 중 둘은 CRLF 파일에 여러 줄 패턴을 써서 적용되지 않았고, 한 줄 패턴으로
  다시 걸어 확인했다.
- AppService로 기본값과 사용자 설정값이 클라이언트 브레이커까지 전달됨을 확인했다.
- 전체 pytest: 150 passed, 새 실패 없음.

## 미해결

- 3회·5분·30분은 로그 근거 없이 정한 초기값이다. 실제 과부하 지속 시간을 보고 조정해야 한다(T8).
- 브레이커는 모델을 구분하지 않는 전역 상태다. 한 작업에서 모델 하나만 쓰는 현재 사용 방식에서는 문제가 없다.
- 과부하 동안 실패한 청크는 늘어난다. 이어하기로 다시 처리되는지는 코드로만 확인했다.
