## 배경

분할을 검열 전용으로 좁힌 직후, 사용자가 이진 분할을 끌 수단이 실제로 있는지 점검을 요청했다.
분할 진입점을 모두 훑으니 네 곳이었고 그중 하나가 스위치를 보지 않고 있었다.

## 문제

앞 작업에서 검열 분기에는 `use_content_safety_retry` 게이트를 붙였으나, 같은 함수의 JSON 파싱 실패
분기는 빠뜨렸다. 이 분기는 예외 처리가 아니라 반환값 검사라 `except` 블록을 손볼 때 눈에 들어오지
않았다. 그 결과 무결성 모드 사용자는 GUI 체크박스를 꺼도 모델이 JSON을 제대로 돌려주지 못하면
최대 7회까지 쪼개며 요청하게 된다. RPM 1.8에서는 청크 하나에 4분 가까이 걸린다.

점검 과정에서 GUI의 "최대 분할 시도"·"최소 청크 크기" 스핀박스가 무결성 모드에 전혀 영향이 없다는
것도 드러났다. 이들은 레거시 텍스트 경로와 강제 분할 경로 전용이고, 무결성 깊이는 GUI에 노출되지
않은 `max_integrity_retry_depth`가 정한다.

## 결정과 근거

- 파싱 실패 분할을 `use_content_safety_retry`에 묶는다. 사용자 판단으로, 이 분기는 검열의 다른
  표현으로 본다. Gemini가 검열 시 빈 응답이나 깨진 응답을 돌려주기도 해서 실질적으로 같은 갈래다.
  대안은 `max_integrity_retry_depth`를 GUI에 노출해 깊이로 조절하게 하는 것이었으나, 손잡이를 늘리는
  대신 기존 체크박스 하나가 무결성 분할 전체를 끄는 쪽을 택했다.
- 스위치가 꺼져 있으면 원문을 유지한다. 검열 분기는 같은 상황에서 예외를 전파하는데, 파싱 실패는
  예외가 아니라 반환값 검사여서 던질 객체가 없다. 깊이 한도에 걸렸을 때의 기존 동작과 맞췄다.
  두 분기의 OFF 동작이 비대칭이지만, 검열 전파는 이미 병합된 동작이라 이번에 함께 바꾸지 않았다.
- 툴팁에 파싱 실패도 함께 꺼진다는 점과 끄면 원문이 남는다는 점을 적었다. 라벨은 그대로 뒀다.

## 검증

- 회귀 테스트 2개 추가. 스위치가 꺼져 있으면 파싱 실패에도 호출이 1회에 그치고 원문이 남는지,
  켜져 있으면 8항목이 1+2+4회로 쪼개지는지.
- 관련 스위트 115 passed.
- GUI 수명주기 테스트 3건이 실패했으나 기준선을 같은 테스트 조합으로 다시 돌려 동일하게 실패함을
  확인했다. 단독 실행하면 통과하므로 Qt 인스턴스를 공유하는 테스트 격리 문제이고 이번 변경과 무관하다.
  처음에는 툴팁 변경 탓으로 판단했는데, 기준선을 다른 조합(해당 파일 단독)으로 돌린 탓이었다.

## 미해결

- 파싱 실패가 검열 때문인지 모델의 형식 이탈 때문인지는 여전히 구별하지 못한다. 스위치를 끈 사용자는
  형식 이탈로 실패한 청크도 복구 시도 없이 원문으로 받는다.
- GUI 스핀박스 두 개가 무결성 모드에서 무의미한 상태는 그대로 남았다. 무결성 깊이 설정은 여전히
  파일을 직접 고쳐야 한다.
- 검수 화면의 강제 분할 재번역은 스위치를 보지 않는다. 사용자가 버튼으로 명시 요청한 분할이라
  의도한 것으로 보고 두었다.
- GUI 수명주기 테스트의 격리 결함은 손대지 않았다.
