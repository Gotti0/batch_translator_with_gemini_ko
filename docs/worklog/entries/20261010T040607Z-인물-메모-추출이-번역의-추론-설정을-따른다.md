## 배경

배치 수거 결과에서 인물 메모를 추출하지 않도록 바꾼 앞 작업(20261010T035423Z)에서 미해결로 남긴 항목이다. 같은 실사용 로그에서 추출 요청마다 "Thinking Level='HIGH'"가 찍혔고, 건당 30초에서 4분 30초가 걸렸다.

## 문제

추출기는 생성 설정에 temperature, 응답 형식, 스키마만 넣고 추론 설정은 넘기지 않았다. Gemini 클라이언트는 thinking level이 없으면 Gemini 3에 HIGH를 기본으로 건다. Gemini 2.5는 thinking budget이 없으면 -1(동적)을 쓴다. 번역과 용어집 추출은 설정의 thinking_level과 thinking_budget을 넘기므로, 인물 메모 추출만 사용자 설정과 무관하게 돌았다.

다른 프로바이더(OpenAI 호환, Ollama, CLI)는 클라이언트를 만들 때 설정에서 추론 강도를 읽고, 추출 클라이언트도 같은 설정으로 만들어진다. 그래서 그쪽은 원래 번역 설정을 따르고 있었다. 빠진 곳은 Gemini뿐이었다.

## 결정과 근거

- 추출 요청에 번역 설정의 thinking_level(생성 설정 안)과 thinking_budget(인자)을 넘긴다. 용어집 추출과 같은 방식이다. 다른 프로바이더는 생성 설정의 thinking_level 키를 쓰지 않으므로 동작이 바뀌지 않는다. 번역도 같은 키를 모든 프로바이더에 넘기고 있다.
- 사용자에게 세 가지를 제시했고 사용자가 고른 것은 번역 설정을 따르는 방식이다.
  - 택하지 않음: 추출 전용 설정(기본 low)을 설정 탭에 두는 방식. 추출 모델을 따로 고르는 기존 설계와는 맞지만 설정 항목이 늘어난다.
  - 택하지 않음: 설정 없이 low로 고정하는 방식. 품질이 부족할 때 올릴 방법이 없다.
  - 트레이드오프: 번역을 high로 두면 추출도 high라 속도와 비용은 지금과 같다. 추출을 가볍게 하려면 번역 단계를 낮추거나, 추출 모델로 더 싼 모델을 지정해야 한다.
- 추출 모델을 따로 지정했는데 번역 설정의 단계를 그 모델이 지원하지 않으면, 그 모델의 기본값을 쓴다. 예를 들어 Flash 번역의 minimal을 Pro 추출 모델에 넘기면 high가 된다. 설정 탭이 번역 모델을 바꿀 때 쓰는 규칙(지원하지 않는 단계면 그 모델의 기본값)과 같다. 그대로 넘기면 매 요청이 잘못된 인자로 실패한다. 가까운 단계로 바꾸는 방법(minimal을 low로)도 있었으나, 설정 탭과 규칙이 갈라지므로 택하지 않았다.

## 검증

- 단위: 추론 설정을 받으면 생성 설정의 thinking_level과 thinking_budget 인자로 넘기고, 받지 않으면 둘 다 넘기지 않는다(클라이언트 기본값).
- 통합: AppService가 만든 추출기가 번역 설정(low, 512)을 갖는다. 추출 모델을 Pro로 바꾸면 minimal이 high로, 추출 모델을 비우면 minimal 그대로다.
- 수정 전 코드에서 새 테스트 3개가 실패하는 것을 확인했다.
- 추출기가 만든 생성 설정을 실제 Gemini 클라이언트 설정 조립에 넣어 ThinkingLevel.LOW와 JSON 스키마가 실리는 것을 확인했다(네트워크 없음).
- 전체 테스트: 507 passed, 7 skipped (프로젝트 가상환경, Python 3.10.11).
- 실제 API에서 추출 속도가 얼마나 달라지는지는 확인하지 않았다.

## 미해결

- 추출기는 번역과 다른 스케줄러를 쓰므로, 추출 요청과 번역 요청이 다른 키로 동시에 나갈 수 있다.
