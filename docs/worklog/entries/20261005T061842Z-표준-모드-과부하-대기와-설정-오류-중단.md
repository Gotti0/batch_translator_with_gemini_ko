## 배경

번역 중단 뒤 원문 배열이 어긋나는 세 경로를 고친 뒤 실제 Gemini API로 검증했다. 검증 중 gemini-3.8-flash와 3.7-flash 모두 503 과부하를 길게 돌려주었고, 같은 증상으로 끝나는 경로가 둘 더 드러났다.

## 문제

1. 표준 모드는 503 재시도까지 실패한 청크를 실패로 기록하고 다음 청크로 넘어갔다. 2026-09-19 결정("호출부는 그 청크만 실패로 남기고 작업을 계속한다")을 따른 것이다. 과부하가 이어진 실호출에서 남은 청크 셋이 모두 "실패 문구 + 원문"으로 채워졌고 상태는 completed로 끝났다. 제보된 증상과 같은 결과물이다. 무결성·EPUB은 2026-09-20에 과부하를 성공할 때까지 기다리도록 바뀌었지만 표준 모드는 그 결정에 포함되지 않았다. 검열 분할 중 서브 청크가 과부하를 만나면 "[서브 청크 N 번역 오류]" 자리표시로 삼켜져 그 청크가 완료로 기록되는 구멍도 있었다.
2. 프롬프트 템플릿에 {{slot}}이 없으면 모든 청크가 즉시 같은 오류로 실패했고, 이것도 "실패 + 원문"으로 채워진 채 완료됐다. 오류 문구는 "작업을 중단합니다"라고 말하지만 앱 계층이 일반 번역 실패로 받아 청크 실패로 적었다. 키 소진과 같은 의도와 동작의 어긋남이다.

## 결정과 근거

- 표준 모드도 과부하 청크를 성공할 때까지 같은 자리에서 다시 시도한다. 무결성·EPUB이 쓰던 대기 루프를 시도 함수를 받는 일반형으로 바꿔 세 모드가 같은 루프를 쓴다. 상한 없음, 매 회 중단 확인, 간격은 서킷브레이커와 스케줄러에 맡김이라는 방침은 그대로다. 표준 경로는 과부하를 BtgApiClientException에 감싸서 올리므로 예외 사슬을 따라 판단한다.
- 검열 분할 중 서브 청크의 과부하는 자리표시로 남기지 않고 올려, 청크 전체를 처음부터 다시 시도한다. 이미 번역한 서브 청크를 버리고 검열 분할도 다시 겪는 비용이 든다. 대신 무결성 경로(분할 재귀 중 과부하를 올려 청크 전체 재시도)와 같은 규칙이 되고, 부분 결과를 보존하는 별도 상태가 필요 없다.
- 프롬프트 템플릿 오류는 전용 예외(BtgPromptTemplateException)로 올리고, 앱 계층은 키 소진과 같은 작업 중단 신호로 다룬다. 전용 예외는 BtgTranslationException을 상속해 기존 처리부와 호환된다. 시작 전에 템플릿을 미리 검사하는 방안도 있었지만, 첫 청크에서 같은 신호로 멈추면 요청이 나가기 전에 끝나고 검증 로직을 두 곳에 두지 않아도 된다.

## 검증

- 회귀 테스트 7건 추가. 과부하 뒤 같은 청크 재시도(검열 재시도 켬/끔), 분할 중 과부하 시 자리표시 없음, 과부하 아닌 오류는 기다리지 않음, 대기 중 취소, 앱 수준에서 과부하가 끼어도 출력에 원문 없음, 템플릿 오류 시 API 호출 없이 중단. 수정 전 코드에서는 이 중 6건이 실패했다.
- 실호출 검증 결과(같은 날): 실제 하루 한도 429를 받은 표준 모드가 실패 기록 없이 멈췄고, 중단 직후 재시작에서 남은 청크 Task 4개가 정리돼 대기 청크를 겹쳐 번역하지 않았다. 과부하 대기 자체는 실호출로 다시 확인하지 않았다(3.7-flash 하루 한도 소진).

## 미해결

- 과부하가 풀리지 않으면 표준 모드도 그 청크에서 무한히 머문다. 무결성·EPUB과 같은 위험이며 사용자가 감수하기로 한 것이다. 표준 모드는 이 대기를 진행률 창에 따로 표시하지 않고 로그로만 남긴다.
- 실호출에서 config의 프리필 프롬프트가 번역 대신 다른 응답("Please provide the scene…")이나 9배 길이의 재작성을 돌려줬고, 성공으로 기록됐다. 프롬프트 내용의 문제라 코드로 고치지 않았다. 번역이 아닌 응답을 일반적으로 가려낼 기준은 없고, 검토 탭의 길이 비율 검사가 사후 확인을 맡는다.
- Gemini 외 프로바이더의 사용량 제한은 여전히 청크 실패로 기록된다.
