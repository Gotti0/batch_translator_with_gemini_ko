## 배경

사용자가 실행 로그(run_20260920_024812_36728)의 흐름 설명을 요청했다. 57청크 작업이 3번째 청크에서
`gemini-3.8-flash`의 503 과부하에 걸렸고, 그 실패에 Binary Split이 반응해 200 → 100 → 50으로 청크를
쪼개고 있었다. 사용자가 이 분할은 검열 재시도 전용으로 의도한 설계라고 밝혔다.

## 문제

무결성 경로 `_translate_integrity_chunk_with_retry`는 `except Exception` 하나로 모든 오류를 받아
분할로 보내고 있었다. 레거시 텍스트 경로는 "콘텐츠 안전 문제" 문자열을 확인해 검열만 걸러내므로,
같은 기능의 두 구현이 서로 다른 조건으로 동작하고 있었다.

1. 503 과부하는 청크 크기와 무관한 서버측 문제인데 분할로 요청 수만 배로 늘렸다. RPM 1.8 전역 제한과
   과부하 서킷브레이커 정지가 겹쳐, 쪼갠 조각들이 대기열을 잡아 작업이 정체된다.
2. 키·재시도 소진 예외는 클라이언트가 작업 전체를 멈추라는 뜻으로 일부러 re-raise한 것인데, 이 포괄
   처리가 삼킨 뒤 깊이 한도에서 원문을 반환했다. 키가 모두 소진돼도 작업은 계속 돌고 결과물은 조용히
   원문으로 채워진다.
3. GUI의 "검열 오류 시 청크 분할 재시도" 체크박스(`use_content_safety_retry`)를 무결성 경로만 읽지 않아
   꺼도 분할이 일어났다.
4. JSON 파싱 실패 분기에는 깊이 검사가 아예 없어, 항목 1개가 될 때까지 무제한으로 쪼갤 수 있었다.
   189항목이면 8단계, 400회 가까운 호출이 가능하다.
5. 재귀 경로가 둘(누락분만 다시 묻는 Targeted Retry, 청크를 쪼개는 Binary Split)인데 `depth` 인자
   하나를 공유했다. 누락이라는 무관한 사건이 검열 분할의 깊이를 잠식하고, 반대로 깊이 내려간 조각에서는
   누락 재시도가 막혀 해당 항목이 빈 문자열로 남았다.

## 결정과 근거

- `except Exception`을 예외 종류별로 나눴다. 키 소진 계열과 503은 re-raise해 각각 작업 중단과 청크 실패로
  끝내고, 검열만 분할로 보낸다. 그 밖의 예외도 전파한다. 분할이 의미 있는 것은 문제 구간이 분리되면
  나머지가 통과할 수 있는 검열뿐이다.
- JSON 파싱 실패 분할은 사용자 확인에 따라 유지했다. 검열 시 Gemini가 빈 응답이나 깨진 응답을 돌려주기도
  해서 실질적으로 같은 갈래다. 다만 깊이 상한을 걸어 폭주만 막았다.
- `depth`를 `split_depth`와 `retry_depth`로 나눴다. 둘은 성격이 다르다. 분할 깊이는 청크 크기의 로그에
  대응해 상한이 의미가 있고, 누락 재시도는 대상이 이미 좁혀져 있어 크기와 무관한 횟수다. Targeted Retry는
  `split_depth`를 그대로 물려주어 누락분 재요청이 검열당하면 남은 분할 예산 안에서 쪼갤 수 있게 했고,
  Binary Split은 조각의 `retry_depth`를 0으로 되돌린다. 조각은 각각 새 요청이고, 분할 깊이 상한이 조각
  수를 묶으므로 총 호출 수도 유한하다.
- 누락 재시도 한도는 새 설정 `max_integrity_targeted_retry_depth` 기본 1로 뒀다. 예산을 나누면 최악의
  호출 수가 늘어나는데, 누락분은 대상이 좁아 한 번이면 대체로 충분하므로 여기서 상쇄한다. 기존 공유
  한도였던 2를 그대로 두면 무료 티어 쿼터를 더 쓴다. 넉넉히 주고 싶으면 설정으로 올린다.
- 누락이 재시도 한도에 걸렸을 때 해당 id를 원문으로 채우도록 했다. 이전에는 map에 키가 아예 없어 상위에서
  빈 문자열로 남았다.
- 코드에만 하드코딩돼 있던 `max_integrity_retry_depth`를 설정 기본값에 올렸다. GUI 노출은 하지 않았다.

## 검증

- 회귀 테스트 6개를 추가했다. 누락 재시도 뒤 검열이 나도 분할이 살아있는지(호출 4회), 누락 재시도가 자체
  한도에서 멈추고 원문을 남기는지, 검열이 계속될 때 분할이 정확히 1+2+4회에서 멈추는지, 검열 재시도를 끄면
  분할 없이 전파되는지, 503과 키 소진이 분할 없이 1회 호출로 끝나는지.
- 기존 `test_integrity_progress.py`가 목을 `generate_text`로 걸어놨는데 실제 코드는 `generate_text_async`를
  부른다. 목이 일반 MagicMock을 돌려줘 await에서 TypeError가 났고, 기존 `except Exception`이 이를 삼켜
  원문 유지로 통과시키고 있었다. 이 테스트는 그동안 API 응답 경로를 전혀 검증하지 못했다. 목 이름을
  바로잡아 실제 경로를 타게 했다.
- 관련 스위트 112 passed. 남은 1건 `test_censorship_strategies.py`는 존재하지 않는 `translate_text`를
  호출하는 것으로 변경 전부터 실패했고, git stash로 기준선을 확인했다.

## 미해결

- 실제 검열 응답으로 분할이 복구에 성공하는지는 목으로만 확인했고 실행 확인은 하지 않았다.
- 누락 재시도 한도 1은 로그 근거 없이 정한 값이다. 누락이 잦은 모델에서 원문 잔존이 늘어나는지 봐야 한다.
- JSON 파싱 실패가 검열 때문인지 모델의 형식 이탈 때문인지는 여전히 구별하지 못한다. 두 경우의 적정 분할
  깊이가 다를 수 있다.
- 테스트 수집 단계에서 깨지는 모듈이 여럿 남아 있다(`test_resume_verification.py` 인코딩 손상,
  `infrastructure.gemini_batch_client` 모듈 부재). 이번 작업에서 손대지 않았다.
