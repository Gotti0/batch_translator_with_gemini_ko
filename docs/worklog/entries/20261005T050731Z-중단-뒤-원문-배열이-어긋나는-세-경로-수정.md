## 배경

외부 사용자 제보는 한 줄이었다. 번역이 중단되면 중단 지점 뒤쪽 원문 배열이 망가진다. 모드도, 결과 파일에서 봤는지 검토 탭에서 봤는지도 알 수 없었다. 그래서 중단 지점 뒤가 원문과 어긋날 수 있는 경로를 코드에서 찾고, 가짜 번역 함수로 각각 재현했다. 실제로 재현된 경로는 셋이었다.

## 문제

1. 표준 모드는 모든 키가 소진돼도 작업을 멈추지 않았다. 도메인 계층은 키 소진을 작업 중단 신호로 다시 던지는데, 앱 계층의 청크 함수가 이를 API 오류 하나로 받아 그 청크의 실패로 기록했다. 남은 청크가 같은 이유로 곧바로 실패하며 "실패 문구 + 원문"으로 채워졌고, 이것이 병합돼 "번역 완료"로 끝났다. 출력 뒤쪽은 청크마다 오류 문구로 잘린 원문이었다. 후처리가 이 원문의 빈 줄과 태그 모양 문자열까지 바꿔 줄 배치도 달라졌다. 무결성 모드는 같은 상황에서 작업을 멈추므로 두 모드의 방침이 어긋나 있었다. 검열 분할 도중의 키 소진도 "[서브 청크 N 번역 오류]" 자리표시로 삼켜져, 그 청크가 완료로 기록되는 구멍이 따로 있었다.
2. 표준 모드에서 중단하면 바깥 Task만 취소되고, create_task로 띄운 청크 Task는 남았다. 세마포어에서 기다리던 Task는 취소 신호를 보고 빠지지만, 사용자가 진행 중인 요청이 끝나기 전에 다시 시작하면 취소 신호가 지워져 그대로 번역을 이어 갔다. 10청크·동시 3개로 6번째 청크 시점에 중단하고 바로 재시작하자 API 호출이 17회 나갔다(필요한 것은 10회). 청크 크기를 바꿔 재시작하면 새 실행이 청크 파일을 비운 뒤 옛 경계의 번역이 같은 번호로 끼어들 수 있다. 청크 함수의 finally에 있던 return이 CancelledError를 삼키는 문제도 겹쳐 있었다.
3. 무결성 검토 탭의 저장은 번역된 청크 수만큼 range로 돌며 이어 붙였다. 중단으로 청크가 빠져 있으면 그 뒤 줄이 앞으로 당겨지고 마지막 청크가 잘렸다. 중간이 비어 있지 않아도 중단 지점 뒤 원문이 통째로 빠졌다. 최종 파일 생성은 경로만 돌려줬는데, 중단된 작업에는 결과 파일이 없거나 이전 실행의 파일이 남아 있었다.

## 결정과 근거

- 키·재시도 소진은 표준 모드에서도 작업을 멈춘다. 그 청크는 완료로도 실패로도 기록하지 않고 메타데이터 상태도 완료로 바꾸지 않아, 이어하기가 남은 청크를 처음부터 번역한다. 무결성 모드와 같은 방침이다. 키 소진이 아닌 API 오류는 지금처럼 "실패 문구 + 원문"을 남긴다. 판단 기준은 GeminiAllApiKeysExhaustedException(재시도 소진 포함)이며, 예외 사슬을 따라 확인한다.
- 소진을 만난 뒤 세마포어를 넘겨받은 청크는 요청을 시작하지 않는다. 메인 루프가 남은 Task를 정리하기 전에 다음 청크가 요청을 보낼 수 있기 때문이다. 가짜 함수로 재현했을 때는 이 틈에 남은 청크가 모두 시도됐다.
- 청크 루프를 어떤 이유로 빠져나오든 남은 청크 Task를 취소하고 끝날 때까지 기다린다. 이 때문에 중단 시점에 진행 중이던 요청의 결과는 버린다. 스케줄러가 API 요청을 한 번에 하나만 보내므로 버려지는 요청은 많아야 하나다. 반대로 끝까지 두면 새 실행과 겹쳐 같은 청크를 다시 보내고, 청크 경계가 바뀐 경우 결과물에 끼어든다.
- 청크 함수의 finally에서 return을 없앴다. 중단과 키 소진은 그 청크의 결과가 아니므로 진행 수·실패 수·메타데이터 기록을 건너뛴다. 빈 청크의 조기 return은 예전처럼 finally의 집계를 거친다.
- 무결성 검토 탭은 원문 청크 순서로 결과 파일을 쓰고, 번역이 없는 청크 자리에는 원문을 둔다. 번역 파이프라인의 조립 규칙(번역이 없는 줄은 원문)과 맞춘 것이다. 같은 이유로 청크 결과에 없는 줄도 빈 문자열 대신 원문으로 읽는다. 최종 파일 생성도 경로만 돌려주지 않고 현재 청크로 파일을 다시 쓴다.

버린 접근:

- 실행마다 별도 취소 토큰을 두어, 이전 실행의 Task가 지워지지 않은 자기 신호를 보고 빠지게 하는 방안. 진행 중이던 요청의 결과는 살릴 수 있다. 하지만 새 실행은 그 청크가 아직 진행 중인 줄 모르고 다시 번역하므로 중복이 남고, 청크 경계가 바뀐 경우의 끼어들기도 막지 못해 버렸다.
- 안쪽 try에서 키 소진을 잡아 다시 던지는 방안. 다시 던진 예외를 바깥의 API 오류 처리가 받아 "실패 + 원문"으로 기록해 버리므로, 바깥 처리부 맨 앞에서 확인하도록 바꿨다.

## 검증

- 재현 스크립트 세 개로 수정 전 동작을 확인했다. 키 소진 뒤 예외 없이 끝나며 청크마다 오류 문구와 원문이 남았고, 중단 직후 청크 Task 7개가 살아 있었으며, 검토 탭 저장 결과가 T0~T3, T6, T7로 당겨지고 잘렸다.
- 회귀 테스트 7개를 더했다. 수정 전 코드에서는 7개 모두 실패하고, 수정 후에는 통과한다. 키 소진 시 작업 중단과 이어하기 완료, 동시 작업 중 소진 시 Task 정리, 중단 직후 재시작 시 중복 번역 없음, 검열 분할 중 소진 전파, 검토 탭 저장의 중간 공백과 꼬리 보존, 최종 파일 생성이 여기에 해당한다.
- 전체 스위트: 476 passed, 7 skipped.
- 실제 Gemini API로 키를 소진시키는 실호출 검증은 하지 않았다. 소진 예외는 가짜로 주입했다.

## 미해결

- 제보자가 어느 모드에서 무엇을 봤는지는 확인하지 못했다. 세 경로 모두 재현됐으므로 함께 고쳤다.
- Gemini 외 프로바이더(CLI·OpenAI 호환·Ollama)의 사용량 제한은 BtgApiRateLimitException 등으로 올라온다. 표준 모드에서는 이것이 여전히 청크 실패로 기록돼, 구독 한도가 끝나면 1번과 같은 모양이 될 수 있다. 무결성 모드는 이 예외로 작업을 멈춘다. 프로바이더별로 일시 제한과 소진을 가르는 기준이 필요해 이번 범위에서 뺐다.
- 표준 검토 탭의 최종 파일 생성은 번역된 청크만 이어 붙이므로, 중단된 작업에서는 뒤쪽이 빠진다. 미완료 경고에 사용자가 동의한 뒤의 동작이고 줄 정렬이 핵심인 모드가 아니어서 그대로 두었다.
