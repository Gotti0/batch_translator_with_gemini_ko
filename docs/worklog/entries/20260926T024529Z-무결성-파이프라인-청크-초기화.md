## 배경

검토 탭의 선택 청크 초기화는 메타데이터의 translated_chunks와 failed_chunks에서 번호를 지우는 것으로만 구현되어 있었다. 표준 파이프라인은 이어하기를 이 메타데이터로 판단하므로 그것으로 충분했다.

## 문제

무결성 파이프라인은 이어하기를 임시 폴더의 청크 결과 JSON 존재 여부로 판단하고, 번역 기억도 그 파일들에서 복원한다. 초기화 뒤 다시 번역하면 해당 청크를 JSON에서 읽어 건너뛰었고, 결과 파일은 초기화 전과 같았다. 검토 탭에서는 상태가 대기로 바뀌었지만 번역문은 JSON에서 그대로 보이는 모순된 상태가 되었다.

여기에 무결성 진행 콜백이 성공 개수 N을 받아 0부터 N-1까지를 성공으로 채우는 문제가 겹쳤다. 완료가 앞에서부터 연속이라는 가정인데, 중간 청크가 빈 채로 작업이 멈추면 빈 번호가 성공으로 찍히고 실제 완료된 뒷번호는 빠진다. 초기화한 번호도 이 경로로 되살아났다.

## 결정과 근거

초기화를 리뷰 provider의 메서드로 옮겼다. 기본 구현은 기존처럼 메타데이터만 지우고, 무결성 provider는 청크 결과 JSON을 먼저 지운 뒤 메타데이터를 갱신한다. 파일 삭제가 실패하면 메타데이터를 건드리지 않아, 메타데이터만 초기화되고 JSON이 남는 원래의 불일치가 재발하지 않게 했다. 파이프라인마다 이어하기 기준이 다르므로 그 기준을 아는 provider가 지우는 편이 GUI에서 분기하는 것보다 맞다고 판단했다.

진행 DTO에 완료 청크 번호 목록을 선택 필드로 추가하고, 무결성 진행 콜백은 translated_chunks를 그 목록에 맞춰 다시 만든다. 이미 있던 항목의 상세 정보는 보존한다. 개수만 넘기는 기존 필드는 다른 파이프라인과 GUI 진행률이 쓰므로 그대로 두었다. 청크 설정이 바뀌어 범위를 벗어난 옛 JSON은 완료 목록에서 제외한다.

## 검증

실제 AppService 무결성 번역을 가짜 모델로 돌리는 테스트를 추가했다. 네 청크를 번역한 뒤 한 청크를 초기화하고 다시 돌리면 모델 호출이 한 번만 일어나고 해당 줄만 새 번역으로 바뀐다. 초기화한 청크에서 실패하도록 해 작업을 멈추면 메타데이터에 그 번호가 남지 않는다. 이 검사는 진행 콜백 수정 전 코드에서 네 번호가 모두 성공으로 찍혀 실패하는 것을 확인했다. 전체 테스트는 통과했다.

## 미해결

초기화는 번역 기억 저장소의 해당 청크 기록을 지우지 않는다. 재번역 시 기록이 덮어써지는지, 재번역 전까지 옛 번역이 다른 청크의 예시로 주입되는지는 확인하지 않았다. EPUB provider의 초기화는 기본 구현(메타데이터만)을 그대로 쓰며, EPUB 이어하기 기준과 맞는지는 검토하지 않았다. GUI에서 버튼을 직접 눌러 보는 확인은 하지 않았다.
