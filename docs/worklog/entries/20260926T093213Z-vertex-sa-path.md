## 배경

이전 항목은 설정 탭 Vertex 토글을 고치면서 백엔드 인증 경로가 연결되어 있다고 보고 실제 호출은 검증하지 않았다. 서비스 계정 JSON으로 실호출을 해 보니, 클라이언트에 JSON을 직접 넘기면 asia-northeast3와 global 모두에서 모델 조회와 번역이 성공했지만 앱이 쓰는 팩토리 경로에서는 실패했다.

## 문제

팩토리는 Vertex가 켜져 있고 서비스 계정 경로가 있으면 인증 정보로 경로 문자열 자체를 넘겼다. 클라이언트는 문자열을 JSON으로 파싱해 서비스 계정이면 Vertex, 아니면 API 키로 해석하므로 경로가 API 키가 되었고, 호출은 Gemini Developer API에서 API_KEY_INVALID로 거부됐다. 설정 로드 경로는 파일을 읽어 내용을 넘기고 있었으나 팩토리가 이를 경로로 덮어썼다. 멀티 프로바이더 도입으로 팩토리가 생긴 뒤 Vertex 모드는 앱에서 한 번도 동작하지 않았던 것으로 보인다. 이전 항목의 "백엔드 인증 경로가 연결되어 있다"는 판단은 틀렸다.

## 결정과 근거

- 파일 읽기를 팩토리에 둔다. 앱이 이미 넘기는 인증 정보를 우선하는 방법도 있었으나, 헬스체크·모델 목록 조회·인물 메모 추출기는 인증 정보 없이 설정만 팩토리에 넘기므로 그 경로들이 계속 깨진다.
- 파일을 읽지 못하면 경고를 남기고 호출자가 넘긴 인증 정보로, 그것도 없으면 설정의 API 키로 넘어간다. 설정 로드 경로가 경로 무효 시 auth_credentials로 대체하던 기존 동작과 맞췄다. 대신 경로가 틀렸을 때 Vertex 대신 API 키 모드로 조용히 전환될 수 있다는 점은 감수했다.

## 검증

- 팩토리 회귀 테스트 2개(인증 정보 없이 서비스 계정 경로만 준 경우 Vertex 모드와 파일의 프로젝트 ID, 파일이 없을 때 넘긴 인증 정보로 대체)가 수정 전 코드에서 실패하고 수정 후 통과했다. 전체 스위트가 통과했다.
- 수정 후 팩토리로 만든 클라이언트로 실제 Vertex(global)에 헬스체크와 gemini-2.5-flash 번역을 호출해 성공했다.
- GUI에서 Vertex를 켜고 번역을 돌리는 확인은 하지 않았다.

## 미해결

- 서비스 계정 없이 ADC를 쓰는 Vertex 모드는 클라이언트가 GOOGLE_GENAI_USE_VERTEXAI 환경 변수로만 판단하므로, 설정의 Vertex 토글만으로는 ADC 경로에 들어가지 않는다. 이번에 고치지 않았다.
- 기본 위치 asia-northeast3에서는 조회되는 모델이 7개이고 global에서는 27개였다. gemini-3 계열을 쓰려면 위치를 global로 두어야 할 가능성이 크지만 기본값은 바꾸지 않았다.
- global에서 gemini-3.8-flash 단문 번역이 약 270초 걸렸다. Thinking Level HIGH 적용과의 관계는 확인하지 않았다.
