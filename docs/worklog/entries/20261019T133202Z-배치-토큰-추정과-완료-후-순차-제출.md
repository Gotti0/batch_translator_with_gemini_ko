## 배경

2026-10-19 사용자는 Cloud Monitoring 사용을 거절하고 앱 대기열 추정치와 기존 배치 완료 후 후속 제출을 요청했다. 앞서 최대 50개로 묶었지만 모든 묶음을 연속 제출하면 큐 토큰은 계속 누적됐다.

## 문제

2026-10-19 확인 시 배치 API의 작업 정보에는 현재 프로젝트 대기열 토큰 사용량이 없었다. 배치별 입력 토큰 수를 추정해 추적해야 하며, 프로세스를 장시간 재우는 방식은 앱 재시작 후 남은 묶음을 잃는다. 자동 조회가 후속 제출까지 맡으면 수동 조회와 겹칠 때 같은 묶음을 두 번 제출할 수도 있다.

## 결정과 근거

- 기존 API 키의 countTokens로 요청별 입력과 시스템 지시문, 파일 파트를 계산하고 합산한다. SDK의 Developer API 경로는 countTokens의 system_instruction 인자를 지원하지 않아 지시문을 contents에 넣어 계산한다. 따라서 서버 대기열 실측값이 아닌 입력 토큰 추정치다. 응답 스키마 등 생성 설정까지 포함한 서버 내부 산정과 일치를 보장하지 않는다.
- 요청당 10초, 한 배치의 추정 전체에 60초 제한을 둔다. 토큰 계산 실패는 UNKNOWN으로 남기며 배치 제출을 막지 않는다. 사용자 취소는 전파해 제출을 중단한다.
- 메타데이터에는 미제출 청크 번호를 보존하고 한 번에 첫 묶음만 제출한다. 기존 작업이 모두 종료되어 수거된 다음 상태 조회에서 다음 묶음을 만든다. 이미 시도한 실패·검열 청크는 후속 자동 제출 대상에 다시 넣지 않는다.
- 모든 요청 원문과 프롬프트를 별도 대기 파일에 복제하는 방법 대신 청크 번호를 저장한다. 후속 제출 전 원문 경계와 설정을 검사하고 설정이 달라졌으면 자동 제출을 멈춘다. 재시작 후에는 기존 용어집 탐색 로직을 재사용한다. 공유 파일은 새 묶음 준비 시 다시 업로드될 수 있다.
- 자동 제출은 이전 제출 키를 유지한다. 취소, 제출 실패, 후속 요청 준비 실패, 제출 여부를 확인하지 못한 작업 유실 시 자동 제출을 중단한다. 취소는 후속 대기 청크부터 비운 뒤 서버 작업 취소를 요청한다.
- AppService의 배치 상태 변경에 공유 비동기 잠금을 적용했다. 자동 조회와 수동 조회가 동시에 완료를 관찰하면 다음 묶음이 두 번 제출되는 경합을 테스트로 재현했으므로 UI 버튼 상태만으로 막지 않는다.
- 로그는 현재 파일의 진행 작업 중 알려진 입력 토큰 합계, 토큰 수 미상 작업 수, 미제출 청크 수를 구분한다. 다른 파일·앱의 작업과 실제 서버 내부 처리량은 포함하지 않는다.

## 검증

- 2026-10-19 전체 테스트 529 passed, 7 skipped, 종료 코드 0. git diff --check 통과.
- 동시 조회 회귀 테스트는 보호 전 2개여야 할 서버 작업이 3개여서 실패했고 공유 잠금 적용 후 통과했다.
- 모의 배치 서버로 앱 재시작과 용어집 복원, 진행 중 후속 제출 금지, 완료 후 다음 묶음 제출, 실패 청크 중복 제출 방지, 취소 및 제출 오류 후 자동 제출 중단, 설정 변경 후 정지를 검증했다.
- SDK ClientError 및 countTokens 모의 응답으로 토큰 합산, 계산 실패 시 UNKNOWN과 제출 유지, 계산 중 취소 시 제출 금지를 확인했다. 실제 설치 SDK의 요청 변환도 네트워크를 대체한 상태에서 시스템 지시문·원문·PDF URI가 countTokens 요청에 들어가는지 확인했다.
- 401개 요청을 최대 50개씩 9묶음으로 나누되 순서와 청크 번호가 보존되는지 확인했다.

## 미해결

- 실제 유료 번역이나 서버 countTokens 호출로 토큰 추정 오차를 측정하지 않았다. 실행 중인 앱은 재시작해야 새 코드가 적용된다.
- 자동 후속 제출은 GUI 상태 조회 또는 CLI의 상태 확인 호출이 실행될 때 진행된다. 앱이 꺼져 있는 동안에는 제출하지 않으며, 재실행 후 같은 파일의 상태 확인으로 이어간다.
- 순차 제출과 로그 집계 범위는 현재 파일의 메타데이터에 기록된 작업이다. 다른 파일·앱·프로세스의 작업까지 프로젝트 전체를 통제하지 않는다. 공유 잠금도 한 AppService 인스턴스 안에서만 유효하다.
- 추정값 자체로 토큰 한도를 보장하지 않는다. 첫 묶음만으로도 서버 할당량을 초과하거나, 다른 작업이 대기열을 차지하면 429가 발생할 수 있다.
