## 배경

설정 탭의 인증·연결 테스트는 결과를 안내창으로만 보여주고 실행 로그에는 남기지 않았다. 로그를 추가한 뒤 Antigravity CLI 헬스체크가 "60초 내 응답 없음"으로 실패하는 것이 드러났다.

## 문제

1. LLM·임베딩 헬스체크는 예외가 났을 때만 로그를 남겼고, 임베딩 쪽은 예외도 기록하지 않았다.
2. 처음에는 시간 초과를 CLI 응답 지연이나 연결 문제로 보았으나, 같은 프롬프트를 앱과 같은 코드 경로로 180초 제한을 두고 직접 호출하자 agy가 약 174초 동안 내부 재시도한 끝에 RESOURCE_EXHAUSTED (code 429)로 종료했다. 원인은 할당량 소진이었고, 60초 제한이 그 오류를 가렸다.
3. 헬스체크는 바깥 asyncio.wait_for로 제한 시간을 거는데, 이때 안쪽 호출에는 TimeoutError가 아니라 취소가 전달된다. CLI 클라이언트는 프로세스 종료를 TimeoutError 경로에만 두었기 때문에 agy 프로세스가 살아남아 호출을 계속했다(실측으로 확인). Claude·Codex 클라이언트도 같은 구조였고, 번역 중지로 인한 취소도 같은 경로를 탄다. agy models 조회도 10초 초과 시 프로세스를 남겼다.
4. Antigravity 클라이언트는 "rate limit"·"too many requests" 문구만 사용량 제한으로 분류해, 429 할당량 소진을 일반 실패로 처리했다.

## 결정과 근거

- 헬스체크 로그는 모든 프로바이더가 거치는 AppService의 두 헬스체크 함수에 넣었다. 각 클라이언트가 돌려주는 진단 메시지를 그대로 남기며, 메시지에 키 개수와 모델 이름만 있고 키 원문은 없음을 확인했다.
- 취소 시 프로세스 종료는 세 클라이언트 모두 CancelledError 경로를 추가해 처리하고, 종료 함수는 공통 기반 모듈 하나에 둔다. 이미 끝난 프로세스는 건드리지 않는다.
- 429 분류는 RESOURCE_EXHAUSTED와 "code 429" 형태만 본다. 오류 ID에 숫자가 섞여 있어 숫자 429만으로 판정하면 오탐이 생길 수 있다.
- 트레이드오프: 헬스체크 제한 시간을 agy 재시도 시간(약 3분)에 맞추면 실제 원인을 볼 수 있지만, 버튼 하나에 최대 3분을 기다려야 한다. 60초를 유지하고 시간 초과 메시지에 할당량 소진 가능성을 안내하는 쪽을 택했다.
- Claude·Codex의 사용량 제한 판정 문구는 두 CLI가 실제로 내는 문구를 확인하지 못해 바꾸지 않았다.

## 검증

- 신규 테스트 중 CLI 프로세스 정리·429 분류·헬스체크 메시지 관련 8개가 수정 전 코드에서 실패하고 수정 후 통과했다. 헬스체크 로그 테스트 4개를 추가했고 전체 스위트가 통과했다.
- 실제 agy로 바깥 제한 시간 4초를 걸어 끊었을 때, 호출 전에는 없던 agy 프로세스가 실행 중에는 떠 있었고 끊은 직후에는 사라졌다.
- GUI 실행 로그에서 세 프로바이더의 헬스체크 시작·결과가 기록되고, Antigravity 시간 초과에 새 안내가 나오는 것을 확인했다. 같은 로그에서 Claude·Codex CLI가 로그인 세션으로 인증에 성공했다.

## 미해결

- GUI에서 시간 초과 후 agy 프로세스가 정리되는지는 판별하지 못했다. 확인 시점이 agy가 스스로 끝났을 시점 이후였다.
- 번역 중지 버튼으로 취소할 때 프로세스가 정리되는지는 직접 확인하지 않았다.
- CLI 클라이언트는 비정상 종료 시 stderr가 있으면 stdout을 로그에 남기지 않는다.
