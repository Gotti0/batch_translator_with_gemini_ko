## 배경

사용자 제보: 새 청크로 넘어갈 때 쓰던 키를 이어 쓰지 않고 첫 번째 키부터 다시 써서 429가 계속 난다. 키 풀은 쿨다운이 아닌 키 중 등록 순서가 가장 앞선 키를 고르므로, 새 청크가 첫 키부터 시작하는 것 자체는 설계대로다. 문제는 하루 한도를 소진한 첫 키가 쿨다운으로 인식되지 않는다는 점이었다.

## 문제

하루·분당 한도 429는 키 전체가 아니라 (키, 모델) 단위로 쿨다운을 건다. 기록할 때는 429 본문의 quotaDimensions.model을, 새 요청이 키를 고를 때는 요청에 쓴 모델명을 썼다. 서버는 preview·alias 모델의 한도를 다른 이름으로 알려준다. 실호출에서 gemini-3.1-pro-preview와 gemini-pro-latest가 모두 gemini-3.1-pro로 돌아왔고, 과거 로그에서도 gemini-3-flash-preview가 gemini-3-flash로 돌아왔다. 두 이름이 다르면 쿨다운이 조회되지 않는다. 같은 요청 안에서는 시도한 키 제외 목록 덕에 다음 키로 넘어가지만, 다음 청크는 다시 첫 키를 골라 429를 맞는다. 키를 모두 소진한 뒤에도 청크마다 모든 키에 헛요청을 보내 RPM 슬롯을 낭비했다.

T5에서 모델 단위 쿨다운을 도입할 때 서버가 알려주는 모델명이 요청 모델명과 같다고 가정한 것이 틀렸다. 정식 이름 모델(gemini-2.5-pro, gemini-3.5-flash 등)은 두 이름이 같아 그동안 드러나지 않았다.

## 결정과 근거

모델 쿨다운은 요청에 쓴 모델명으로 건다. 서버가 준 모델명은 "이 한도가 모델 단위인가"를 알리는 신호로만 쓴다. 조회가 요청 이름으로 이뤄지므로 기록도 같은 이름이어야 한다.

트레이드오프: 서로 다른 alias가 같은 할당량을 공유해도(gemini-pro-latest와 gemini-3.1-pro-preview) 쿨다운을 공유하지 않는다. 한 작업 안에서는 모델이 고정이므로 이 차이가 드러나는 경우는 번역과 인물 메모 추출에 서로 다른 alias를 쓸 때 정도다. 그 경우에도 추출기는 별도 클라이언트와 키 풀을 쓰므로 원래도 쿨다운을 공유하지 않았다. 요청 이름과 서버 이름을 모두 기록하는 방법도 있었으나, 서버 이름으로 조회하는 곳이 없어 효과가 없으므로 택하지 않았다.

## 검증

- 회귀 테스트: 실제 429 본문 형태(위반 네 개, quotaDimensions.model=gemini-3.1-pro)로 gemini-3.1-pro-preview 요청 세 번을 보내면, 첫 키는 첫 요청에서만 호출되고 이후 요청은 둘째 키로 간다. 수정 전 코드에서 실패하고 수정 후 통과하는 것을 확인했다. 전체 스위트가 통과했다.
- 실호출(무료 키 2개, 무료 한도가 0인 gemini-3.1-pro-preview, 할당량 차감 없음): 수정 전에는 청크 2가 키#1→키#2 순으로 다시 429를 받았다. 수정 후에는 청크 1에서 두 키가 모두 쿨다운에 들어간 뒤 청크 2가 요청 없이 곧바로 전 키 소진으로 끝났다.
- 실제 번역 작업에서 한도가 소진되는 순간의 전환은 하루 한도를 써야 해 확인하지 않았다.

## 미해결

- 기간을 알 수 없는 할당량 429(quotaId에 PerDay·PerMinute가 없음)는 100초 쿨다운이라, 실제로는 하루 한도였다면 100초마다 첫 키로 돌아간다. 과거 로그에 3건 있었다.
- 인물 메모 추출기는 별도 클라이언트라 번역 쪽 키 풀의 쿨다운을 모르고 첫 키부터 시도한다. 작업당 키마다 한 번씩 429를 더 받는다.
