## 배경

09-24 설계는 인물 메모 추출용 클라이언트를 따로 만들어 별도 스케줄러로 돌렸다. 번역 속도에 영향을 주지 않으려는 의도였다. 오늘 앞선 두 작업(배치 수거에서 추출하지 않음, 추출이 번역의 추론 설정을 따름)에서 이 문제를 미해결로 남겼다.

## 문제

요청 스케줄러는 Gemini 클라이언트마다 하나씩 있다. 그래서 추출과 번역이 각자 슬롯을 받아 동시에 나갔고, 키도 각자 골랐다. 그 결과 다음 문제가 생겼다.

- 서로 다른 무료 키로 요청이 동시에 나갈 수 있었다. 무료 키 여러 개를 쓰는 사용자에게 남용 판정 위험이 있어 지켜 온 "전역에서 한 번에 하나" 원칙에 어긋난다.
- 두 스케줄러의 요청 빈도를 합치면 사용자가 설정한 RPM의 최대 두 배가 되었다.
- 추출 클라이언트는 번역 쪽 키의 쿨다운을 몰라 키마다 429를 한 번씩 더 받았다(09-28 할당량 쿨다운 항목 20260928T051331Z의 미해결).
- 과부하(503) 정지도 두 클라이언트가 따로 셌다.

## 결정과 근거

- Gemini에서는 추출기가 번역 클라이언트 인스턴스를 그대로 쓴다. 스케줄러, 서킷브레이커, 키 할당량과 쿨다운 상태를 공유한다. 모델은 요청마다 넘기므로 추출 모델을 따로 지정하는 기능은 그대로이고, 할당량 쿨다운도 모델별로 따로 추적된다.
- 버린 접근: 추출용 클라이언트는 따로 두고 스케줄러만 주입하는 방식. 동시 요청은 막지만 키 쿨다운 상태를 공유하지 못해 429 중복이 남고, 팩토리에 인자를 더해야 한다.
- 버린 접근: 번역 요청을 우선하는 방식(대기 중인 번역 요청이 없을 때만 추출). 실시간 번역은 끝날 때까지 다음 청크 요청이 늘 대기하므로 추출이 번역이 끝난 뒤로 밀린다. 그러면 앞 청크의 메모를 뒤 청크에 넣는다는 추출의 목적이 사라진다. 그래서 도착 순서(FIFO)를 그대로 둔다.
- 트레이드오프: RPM 상한에 걸려 있는 동안에는 청크마다 요청이 하나씩 더 슬롯을 차지한다. 그래서 추출을 켜면 번역 시간이 최대 두 배 가까이 늘어난다. 이전에도 같은 키로 추출 요청이 따로 나가 할당량을 쓰고 있었으므로, 숨어 있던 비용이 설정한 RPM 안으로 들어온 것이다. 설정 탭 툴팁과 README의 "번역 속도에 영향 없음"을 고쳤다.
- 추출 요청의 503도 번역과 같은 서킷브레이커에 기록된다. 서버 과부하는 두 요청 모두에 해당하므로 같이 세는 것이 맞다.
- 다른 프로바이더는 지금처럼 추출용 클라이언트를 따로 만든다. 전역 스케줄러가 없고, CLI와 Ollama 클라이언트는 요청마다 넘긴 모델을 무시하고 클라이언트를 만들 때 정한 모델을 쓰기 때문이다.

## 검증

- 통합 테스트: 실제 Gemini 클라이언트와 스케줄러에 가짜 SDK를 붙였다. 실시간 번역 4청크와 추출 4건을 돌려 동시에 진행 중인 요청이 최대 1개인지 확인했다. 수정 전 코드에서는 최대 2개로 실패했다.
- 추출기가 Gemini에서는 번역 클라이언트와 같은 인스턴스를 쓰고, 다른 프로바이더에서는 추출 모델로 클라이언트를 따로 만드는지 확인했다.
- 전체 테스트: 509 passed, 7 skipped (프로젝트 가상환경, Python 3.10.11).
- 실제 API에서 번역 시간이 얼마나 늘어나는지, 키 쿨다운 공유로 429가 줄어드는지는 확인하지 않았다.

## 미해결

- 번역을 중단해도 이미 예약된 추출 작업은 취소되지 않고 계속 돈다. 이제 같은 순서를 쓰므로 동시 요청은 생기지 않지만, 곧바로 다시 시작한 번역이 남은 추출 뒤에 줄을 선다.
- 다른 프로바이더의 추출·번역 동시 요청은 다루지 않았다. OpenAI 호환 클라이언트는 RPM 상태를 인스턴스마다 두므로, 추출용과 번역용 클라이언트가 서로의 요청을 모른다.
